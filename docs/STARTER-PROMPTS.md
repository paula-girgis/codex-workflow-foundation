# ابدأ مشروعك — prompts جاهزة

استبدل `[FOUNDATION]` بمجلد الحزمة بعد فك ZIP، و`[PROJECT]` بمجلد مشروعك وافتحه كنطاق العمل. جهّز brief والمنصات والميزانية/المدة والقيود. الحسابات والوصول مطلوبين فقط عند اختيار خدمة تحتاجهم؛ متكتبش secrets هنا. الأساس يحتاج Python 3.10+ (اتجرب على 3.14.6)، وأدوات التطبيق حسب المشروع.

الـprompts تفوض شغل محلي داخل نطاقها، مش تثبيت اختياري أو نشر أو commit/push أو تعديل global configuration. المساعد يحافظ على الموجود ويتولى JSON والـhashes والأدلة؛ المستخدم يراجع المنتج والتصميم والقرارات الجوهرية.

## Prompt كامل قابل لإعادة الاستخدام

```text
ابدأ شغل مشروع بالبيانات دي:
- FOUNDATION: [المسار الكامل لحزمة codex-workflow-foundation]
- PROJECT: [المسار الكامل لمجلد المشروع]
- IDEA/FEATURE: [فكرة المشروع أو المطلوب]
- PLATFORM: [ويب/Android/iOS/desktop/backend/no UI]
- REPOSITORY: [جديد/موجود؛ اذكر branch أو commit لو مهم]
- CONSTRAINTS: [الوقت، الميزانية، الاستضافة، البيانات، التوافق، الحسابات المتاحة]
- ACCEPTANCE: [كيف أعرف إن النتيجة نجحت]

افتح PROJECT كنطاق العمل. اقرأ تعليماته الحالية وFOUNDATION/START.md وملف profile/state لو موجودين، وافحص الملفات وGit والأدوات فعليًا قبل أي تعديل. لو الأساس غايب استخدم adoption الموثق، واحفظ تعليمات وقرارات المشروع ولا تستبدلها. اكتشف التفاصيل الناقصة التي تغيّر scope أو cost أو platform، واسأل عنها فقط؛ اقترح workflow مناسب (lightweight bug أو standard أو visual) ولا تشغّل مراحل أكبر من الحاجة.

لو فيه UI، اعمل inventory للشاشات والحالات والتفاعلات، ثم wireframe PNGs فعلية لاعتمادي قبل polished PNGs واعتماد منفصل قبل production UI. لو مفيش UI، اشرح إن البوابات البصرية اتخطت. بعد البوابات، ثبّت العقود والمعمارية والمهام ثم نفّذ increments صغيرة واختبر التطبيق الحقيقي في runtime المناسب. افصل design mockups عن runtime screenshots وعن functional tests.

أنت مسؤول عن تحديث project/state.json والـhashes والأدلة والـcheckpoints بعد العمل والفحوص والانتقالات؛ لا تطلب مني تعديل JSON أو حساب hashes. احتفظ بمصدر واحد للحالة، وأوقف dependent work عند فشل gate. لا تكرر عمليات نشر/ترحيل/نشر خارجي غير متأكد منها: افحص نتيجتها أولًا. لا تثبت أدوات أو تستخدم حسابات أو تغيّر global configuration أو تعمل commit/push/deploy إلا بعد تفويض منفصل. كمل كل العمل المحلي المصرّح به، وقدّم الملفات والاختبارات والحدود والخطوة التالية.
```

## A — ويب جديد

```text
ابدأ مشروع ويب في [PROJECT] بهدف [brief والجمهور والقيود]. اقرأ [FOUNDATION]/START.md وتعليمات الهدف وحالته لو موجودة. استخدم adoption الموثق لو الأساس غايب، واختار stack مناسب بدون فرض قالب الـpilot. افحص الأدوات المتاحة. لو فيه UI: اعرض صور wireframes لاعتمادي ثم polished لاعتماد منفصل قبل التنفيذ. أنت تدير profile والخطة والـcheckpoints والأدلة والاختبارات. كمل الشغل المحلي المصرّح به بدون تثبيت اختياري أو نشر أو commit/push.
```

## B — mobile/native

```text
ابدأ مشروع [Android/iOS/desktop] في [PROJECT] بهدف [brief والقيود]. اقرأ [FOUNDATION]/START.md ثم تعليمات الهدف وحالته؛ تبنَّ الأساس بالطريقة الموثقة لو غايب. افحص SDK والجهاز/emulator أو simulator قبل اختيار stack. حافظ على اعتماد صور wireframes ثم polished قبل التنفيذ. اختبر في runtime المنصة؛ Chrome مش إثبات native. أنت تدير profile والـcheckpoints والأدلة وتوضح الإعداد الناقص، بدون تثبيت أو حسابات/توقيع أو نشر تلقائي.
```

## C — feature في repo موجود

```text
أضف [feature ومعيار القبول] في [PROJECT]. اقرأ تعليمات الريبو وGit والـcheckpoint ثم .workflow/START.md؛ لو غايب تبنَّ من [FOUNDATION]/START.md بدون استبدال التعليمات أو القرارات. حافظ على معمارية الريبو وحدد المتأثر فقط. لو بتغير رحلة/layout اعرض صور التعديل للاعتمادات المناسبة مع حفظ baseline السابق. نفذ واختبر increments صغيرة وأنت تدير الحالة والأدلة. بدون نشر أو commit/push أو تثبيت اختياري.
```

## D — bug صغير

```text
صلّح [العطل وخطوات تكراره والسلوك المتوقع] في [PROJECT]. اقرأ تعليماته وGit والـcheckpoint و.workflow/START.md؛ لو غايب تبنَّ من [FOUNDATION]/START.md بمسار bug. استخدم reproduce → fix → verify، بدون discovery شامل أو إعادة تصميم طالما مفيش تغيير جوهري للمنتج/الواجهة. حافظ على الاعتمادات ذات الصلة؛ لو ظهر تغيير جوهري اعرض أثره أولًا. أنت تدير checkpoint والأدلة والفحوص المتأثرة. بدون نشر أو commit/push أو تثبيت اختياري.
```

## E — استئناف بعد إغلاق/quota أو chat جديد

```text
استأنف [PROJECT]. اقرأ AGENTS.md و.workflow/START.md والـprofile وproject/state.json ومراجع قراراته، ثم شغّل resume وافحص الملفات وGit. صالح السجل مع الواقع وحدد المتحقق وغير المتحقق؛ افحص نتيجة العمليات الخارجية قبل تكرارها ولا تفترض process أو agent لسه شغال. حافظ على التفويض واعتمادات التصميم وكمل أول خطوة آمنة. أنت تدير checkpoints والأدلة؛ متطلبش مني إعادة التاريخ أو JSON. لو state ناقص/تالف احفظه وافحص البدائل قبل إعادة بنائه؛ متخمنش إكمال أو موافقة.
```

## F — لون/لوجو/component مشترك

```text
في [PROJECT] غيّر [اللون/اللوجو/المكوّن] إلى [القيمة/asset]. اقرأ التعليمات و.workflow/START.md والـprofile والـcheckpoint وخريطة التصميم؛ لو الأساس غايب تبنَّ من [FOUNDATION]/START.md بأمان. عدّل المصدر المشترك بدل نسخ التعديل على الصفحات. حدد الحالات المتأثرة واحفظ baseline المعتمد. اعرض مراجعة مركزة وخد الاعتماد المناسب لأي تعديل على التصميم المعتمد قبل تنفيذه. اختبر التباين/layout والسلوك المتأثر، وحدّث أنت الأدلة والـcheckpoint.
```

## فحص discovery يدوي قصير — غير متحقق حتى الآن

افتح مشروع متبنّي كـworking directory في جلسة Codex جديدة واطلب:

```text
قبل قراءة أي SKILL.md يدويًا: هل resume-project وvisual-review موجودين في قائمة skills المتاحة للجلسة؟ لو موجودين استخدم resume-project لفحص read-only، وسجل اختياره وتحميله. لو غايبين قول غير مكتشفين؛ قراءة المسار مش نجاح discovery. لا تعدّل ملفات ولا تبدأ شغل جديد.
```

في CLI/IDE افحص `/skills` أو selector عند `$`. لو المهارة مش ظاهرة أعد تشغيل Codex وافحص؛ الواجهة الفعلية حسب النسخة. [توثيق OpenAI](https://learn.chatgpt.com/docs/build-skills) اتراجع 2026-09-27 ويصف `.agents/skills/`، لكنه مش اختبار جلستك. لا تنشئ chat تلقائيًا لإثباته. القراءة الصريحة تفضل fallback مع تسجيل الفرق.
